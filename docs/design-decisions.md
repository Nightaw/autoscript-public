# Design Decisions

## 为什么公开版不追求“文件越多越好”

原始项目里的很多文件都和真实环境强绑定，例如：

- 内网地址与设备清单
- 数据库连接
- 真实业务脚本
- 环境控制脚本

这些内容即使数量很多，也不适合直接进入公开仓库。公开版应该优先保留可证明能力的部分：

- 架构抽象
- 指标提取思路
- 可运行的最小 demo
- 样例输入输出

## 公开版保留了哪些技术价值

### 1. 输出状态卡顿识别

通过 `stopOutput()` / `startOutput()` 配对恢复卡顿区间，适合展示最直接的播放器状态解析思路。

### 2. 多信号卡顿聚类

除了单一状态切换，项目里还会遇到渲染超时、音频超时、显示 idle 等弱信号。公开版通过事件聚类还原“疑似卡顿窗口”，这更贴近真实工程中的指标融合思路。

### 3. 分辨率变化时间线

通过解析解码器日志中的宽高变化，输出规范化分辨率时间线，体现质量指标后处理能力。

## 为什么仓库中不包含 APK

APK 通常不是面试展示的重点，反而有这些问题：

- 二进制本身不可读
- 可能涉及版权或分发权限
- 对回答“你做了什么技术工作”帮助有限

更有价值的是把“如何控制设备、如何采集和分析结果”讲清楚。

## 仓库评估重点

- README 是否能快速说明项目价值
- 仓库是否有可运行示例
- 代码是否体现结构化思维
- 设计取舍和实际难点是否表达清楚
